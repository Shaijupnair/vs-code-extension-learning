# GitHub Copilot Instructions — VS Code Extension Development

> **Scope**: These instructions govern ALL code generated by Copilot in this workspace.
> They cover TypeScript/JavaScript style, VS Code API patterns, architecture,
> security, performance, and testing. Follow every rule strictly and never deviate
> unless a specific inline comment says `// copilot-ignore` with an explanation.

---

## 1. Language & Type Safety

- **Always use TypeScript**. Never generate `.js` files for extension source code.
- Set `"strict": true` in `tsconfig.json`. Never disable strict mode.
- **Never use `any`**. Use `unknown` and narrow with type guards.
- Always define **explicit return types** on every exported function.
- Use `readonly` on properties that are not mutated.
- Use union types (`string | undefined`) instead of implicit `undefined`.
- Use **strict equality** (`===`) everywhere. Never use `==`.
- Use `const` by default. Use `let` only when reassignment is required. **Never use `var`**.
- Use **Optional Chaining** (`?.`) and **Nullish Coalescing** (`??`) instead of verbose `&&` or `||` guards.

**Naming Conventions:**

| Construct | Convention | Example |
|---|---|---|
| Variables / Functions | `camelCase` | `getActiveEditor` |
| Classes / Interfaces / Types | `PascalCase` | `TreeNodeProvider` |
| Boolean variables | `is`/`has`/`can`/`should` prefix | `isEnabled`, `hasError` |
| Constants | `UPPER_SNAKE_CASE` | `MAX_RETRY_COUNT` |
| Private class members | `_camelCase` prefix | `_outputChannel` |

**Interfaces vs Types:**

- Use `interface` for public API shapes and object contracts.
- Use `type` for unions, intersections, mapped types, and primitives.

```ts
// ✅ Correct
interface ExtensionConfig {
  readonly timeout: number;
  readonly logLevel: 'debug' | 'info' | 'error';
}

type LogLevel = 'debug' | 'info' | 'error';

// ❌ Wrong
const config: any = vscode.workspace.getConfiguration('myext');
```

## 2. Module System & Imports

- Use **ES Module** syntax exclusively (`import` / `export`).
- **Never** mix `require()` with `import`.
- Use **named imports**. Avoid `import * as vscode` unless working at the top-level entry.
- Avoid barrel re-exports (`index.ts`) that cause circular dependency risks.
- Group imports: (1) Node built-ins, (2) VS Code, (3) third-party, (4) local.
- **Never** leave unused imports. ESLint `no-unused-vars` must be enabled.
- Do **not** use `namespace` — use ES Modules `import`/`export` instead.

```ts
// ✅ Correct
import * as path from 'path';
import { window, commands, ExtensionContext, Disposable } from 'vscode';
import { MyService } from './services/MyService';

// ❌ Wrong
const vscode = require('vscode');
import * as everything from './utils';
```

## 3. Async & Concurrency

- Always use `async/await`. **Never** use `.then()` / `.catch()` chains.
- Always wrap `await` calls in `try/catch`.
- **Never ignore** a returned `Promise` — always await or explicitly discard with `void`.
- Never block the event loop with synchronous I/O or CPU-heavy operations.
- Use `fs/promises` (Node 18+) or `vscode.workspace.fs` for all file I/O.

```ts
// ✅ Correct
async function readConfig(uri: vscode.Uri): Promise<string> {
  try {
    const bytes = await vscode.workspace.fs.readFile(uri);
    return Buffer.from(bytes).toString('utf8');
  } catch (error: unknown) {
    if (error instanceof Error) {
      outputChannel.appendLine(`[ERROR] readConfig: ${error.message}`);
    }
    throw error;
  }
}

// ❌ Wrong
vscode.workspace.fs.readFile(uri).then(data => process(data));
```

## 4. VS Code Extension Architecture

### 4.1 `extension.ts` — Entry Point Rules

- `activate()` must be **minimal**: register commands, providers, and subscriptions only.
- `deactivate()` must release any resources not managed via `context.subscriptions`.
- **Never** put business logic inside `activate()` directly.
- Register all `Disposable` objects via `context.subscriptions.push(...)`.

```ts
// ✅ Correct activate() pattern
export function activate(context: vscode.ExtensionContext): void {
  const service = new MyService(context);
  const provider = new MyTreeProvider(service);

  context.subscriptions.push(
    vscode.commands.registerCommand('myext.doAction', () => service.doAction()),
    vscode.window.registerTreeDataProvider('myextView', provider),
    service,
  );
}
```

### 4.2 Recommended Project Structure

```
src/
  extension.ts          ← Entry point only
  commands/             ← One file per command
    actionCommand.ts
  providers/            ← Tree, CodeLens, Completion, Hover, etc.
    MyTreeProvider.ts
  services/             ← Business logic, no direct VS Code API calls
    MyService.ts
  utils/                ← Pure utility functions
    logger.ts
    pathUtils.ts
  types/                ← Shared interfaces and type aliases
    index.ts
```

### 4.3 `Disposable` Composition Pattern

Every class that owns resources **must** implement `vscode.Disposable`:

```ts
export class MyService implements vscode.Disposable {
  private readonly _disposables: vscode.Disposable[] = [];
  private readonly _watcher: vscode.FileSystemWatcher;

  constructor() {
    this._watcher = vscode.workspace.createFileSystemWatcher('**/*.ts');
    this._disposables.push(
      this._watcher,
      this._watcher.onDidChange(uri => this._onFileChange(uri)),
    );
  }

  dispose(): void {
    this._disposables.forEach(d => d.dispose());
    this._disposables.length = 0;
  }

  private _onFileChange(uri: vscode.Uri): void {
    // handle change
  }
}
```

## 5. Command Development

- Every command ID in `registerCommand` **must match** the `contributes.commands` entry in `package.json`.
- Use a dedicated file in `src/commands/` for each command.
- Apply user-friendly error messages via `window.showErrorMessage`.
- Use `window.withProgress` for long-running commands.

```ts
// src/commands/analyzeCommand.ts
export async function analyzeCommand(service: MyService): Promise<void> {
  await vscode.window.withProgress(
    {
      location: vscode.ProgressLocation.Notification,
      title: 'Analyzing...',
      cancellable: true,
    },
    async (progress, token) => {
      token.onCancellationRequested(() => service.cancel());
      progress.report({ increment: 0, message: 'Starting...' });
      await service.analyze();
      progress.report({ increment: 100, message: 'Done.' });
    },
  );
}
```

## 6. Tree View & Data Providers

- Implement `vscode.TreeDataProvider<T>` in a dedicated file.
- Fire `_onDidChangeTreeData` to refresh the view.
- Never do heavy computation in `getChildren()` — delegate to a service.
- Use `TreeItem.contextValue` for context-menu visibility control.

```ts
export class MyTreeProvider implements vscode.TreeDataProvider<MyNode> {
  private readonly _onDidChangeTreeData = new vscode.EventEmitter<MyNode | undefined>();
  readonly onDidChangeTreeData = this._onDidChangeTreeData.event;

  constructor(private readonly _service: MyService) {}

  refresh(): void {
    this._onDidChangeTreeData.fire(undefined);
  }

  getTreeItem(element: MyNode): vscode.TreeItem {
    return element.toTreeItem();
  }

  async getChildren(element?: MyNode): Promise<MyNode[]> {
    return this._service.getNodes(element);
  }
}
```

## 7. Webview Development

- Always use `Webview.asWebviewUri()` for all local resource URIs.
- **Never inject raw user input** into HTML. Sanitize everything.
- Always set a strict **Content Security Policy (CSP)** header.
- Use only `postMessage` / `onDidReceiveMessage` for communication — never eval.
- Avoid inline `<script>` tags; use a separate bundled JS file via `asWebviewUri`.
- Persist panel state using `WebviewPanel.webview.html` reassignment or `retainContextWhenHidden`.

```ts
function getWebviewContent(webview: vscode.Webview, extensionUri: vscode.Uri): string {
  const scriptUri = webview.asWebviewUri(
    vscode.Uri.joinPath(extensionUri, 'media', 'main.js'),
  );
  const nonce = getNonce();

  return `<!DOCTYPE html>
<html lang="en">
<head>
  <meta charset="UTF-8">
  <meta http-equiv="Content-Security-Policy"
    content="default-src 'none'; script-src 'nonce-${nonce}'; style-src ${webview.cspSource};">
  <title>My Extension</title>
</head>
<body>
  <script nonce="${nonce}" src="${scriptUri}"></script>
</body>
</html>`;
}

function getNonce(): string {
  let text = '';
  const possible = 'ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz0123456789';
  for (let i = 0; i < 32; i++) {
    text += possible.charAt(Math.floor(Math.random() * possible.length));
  }
  return text;
}
```

## 8. Configuration Management

- Define all settings under `contributes.configuration` in `package.json`.
- Read settings via `vscode.workspace.getConfiguration('myext')`.
- Always provide defaults and validate values before use.
- Listen for changes using `vscode.workspace.onDidChangeConfiguration`.
- **Never hardcode** values that should be configurable.

```ts
interface MyExtConfig {
  timeout: number;
  logLevel: 'debug' | 'info' | 'error';
}

function getConfig(): MyExtConfig {
  const cfg = vscode.workspace.getConfiguration('myext');
  return {
    timeout: cfg.get<number>('timeout', 5000),
    logLevel: cfg.get<'debug' | 'info' | 'error'>('logLevel', 'info'),
  };
}
```

## 9. Error Handling

- **Never swallow errors silently.** Always log and/or surface them.
- Distinguish between user errors (show `window.showErrorMessage`) and programmer errors (throw).
- Use the pattern `if (error instanceof Error)` to safely extract messages.
- Always clean up resources in `finally` blocks.

```ts
// ✅ Correct
try {
  await riskyOperation();
} catch (error: unknown) {
  const msg = error instanceof Error ? error.message : String(error);
  logger.error(`riskyOperation failed: ${msg}`);
  void vscode.window.showErrorMessage(`Operation failed: ${msg}`);
} finally {
  cleanup();
}
```

## 10. Logging Standards

- Create a single `vscode.OutputChannel` per extension (singleton).
- Never use `console.log` in production-ready code. Use the `OutputChannel`.
- Support a debug toggle via configuration (`myext.logLevel`).
- Use structured, consistent log format: `[LEVEL] [component] message`.

```ts
// src/utils/logger.ts
let _channel: vscode.OutputChannel | undefined;

export function getLogger(): vscode.OutputChannel {
  if (!_channel) {
    _channel = vscode.window.createOutputChannel('MyExtension');
  }
  return _channel;
}

export function log(level: 'INFO' | 'DEBUG' | 'ERROR', component: string, msg: string): void {
  const cfg = vscode.workspace.getConfiguration('myext');
  const logLevel = cfg.get<string>('logLevel', 'info');
  if (level === 'DEBUG' && logLevel !== 'debug') { return; }
  getLogger().appendLine(`[${level}] [${component}] ${msg}`);
}
```

## 11. Performance Rules

- **Debounce** event handlers (e.g., `onDidChangeTextDocument`) — never process on every keystroke.
- Cache expensive computation results; invalidate on relevant change events.
- Use `vscode.workspace.fs` (async) for all file operations — never `fs.readFileSync`.
- Use streaming for large file processing — never load entire large files into memory.
- Avoid synchronous loops over large document line ranges in the main thread.
- Use `setTimeout`/`setImmediate` to yield control for non-critical background tasks.

```ts
// ✅ Debounce pattern
import { debounce } from './utils/debounce';

const onDocumentChange = debounce((doc: vscode.TextDocument) => {
  analyzeDocument(doc);
}, 300);

context.subscriptions.push(
  vscode.workspace.onDidChangeTextDocument(e => onDocumentChange(e.document)),
);
```

## 12. Memory & Resource Management

- **Everything that can be disposed, must be disposed.**
- Push all event listeners, watchers, channels, and timers into `context.subscriptions` or a class `_disposables` array.
- Avoid global mutable state. Prefer dependency injection over singletons.
- Set object references to `undefined` or clear arrays after disposal to aid GC.
- Never hold references to `TextDocument` or `TextEditor` beyond their lifecycle.

## 13. Security Rules

- **Never** execute shell commands with unsanitized user input. Use whitelists and validation.
- **Never** use `eval()` or `Function()` constructors.
- **Never** trust workspace files — treat them as untrusted input.
- Handle **Workspace Trust** properly: check `vscode.workspace.isTrusted` before running restricted operations.
- Sanitize all user-provided strings before inserting into HTML, shell commands, or file paths.

```ts
// ✅ Workspace trust guard
if (!vscode.workspace.isTrusted) {
  void vscode.window.showWarningMessage('This feature requires a trusted workspace.');
  return;
}
```

## 15. Node.js API Usage

- Prefer **`fs/promises`** over callback-style `fs`. Never use `fs.readFileSync`.
- Prefer **`vscode.workspace.fs`** over Node `fs` where possible — it works across all VS Code file systems (remote, virtual).
- Always use the **`path`** module for path manipulation. Never use string concatenation for paths.
- Never assume OS-specific path separators — use `path.join()` and `path.normalize()`.

```ts
// ✅ Correct
import * as path from 'path';
import { workspace } from 'vscode';

const filePath = path.join(workspaceRoot, 'config', 'settings.json');
const uri = vscode.Uri.file(filePath);
const content = await workspace.fs.readFile(uri);
```

- Always define `engines.vscode` with the minimum supported version.
- Declare only **specific activation events** — never use `"*"`.
- Prefer `onLanguage`, `onCommand`, `onView`, or `workspaceContains` activation events.
- Declare all contributed commands, menus, keybindings, views, and settings under `contributes`.
- Bundle the extension using `esbuild` or `webpack` with tree-shaking enabled.

- Write **unit tests** for all logic in `services/` and `utils/` — no VS Code API needed there.
- **Mock** VS Code API using `jest-mock` or `sinon`. Never use real VS Code API in unit tests.
- Test file naming: `*.test.ts` co-located with source, or in `src/test/`.

## 19. Code Style & Design Principles

- **Single Responsibility**: One class/function does one thing.
- **Early Return**: Use guard clauses at the top of functions to handle invalid states.
- **Avoid Deep Nesting**: Maximum 2 levels of nesting. Refactor with helper functions.
- **No Implicit Returns** in arrow functions for multi-line logic.
- Use **named functions** for complex logic — avoid anonymous arrow function sprawl.
- Prefer **immutability**: use `Object.freeze`, `readonly`, and `as const` where appropriate.
- Use **destructuring** for cleaner access to objects and arrays.

```ts
// ✅ Early return + destructuring
function processResult(result: AnalysisResult | undefined): string {
  if (!result) { return 'No result'; }

  const { severity, message, location: { line, column } } = result;
  return `[${severity}] ${message} at ${line}:${column}`;
}
```

## 20. Copilot Code Generation Rules

When generating any code in this workspace, Copilot **must** follow these rules:

1. **Always include explicit TypeScript types** — no implicit `any`, no missing return types.
2. **Always include error handling** — every `await` must be in a `try/catch`.
3. **Always include disposal logic** — every `Disposable` must be pushed to `context.subscriptions` or a `_disposables` array.
4. **Never generate global mutable variables** — use class properties or local scope.
5. **Always add JSDoc comments** to exported functions and classes.
6. **Always include inline comments** on non-obvious logic explaining the "why".
7. **Always follow the project folder structure** — commands in `commands/`, logic in `services/`, helpers in `utils/`.
8. **Never use deprecated VS Code APIs** — check the VS Code API reference for `@deprecated` markers.
9. **Always generate unit-testable code** — services must not directly call VS Code APIs.
10. **Explain edge cases** in comments — what happens if the user has no workspace, no active editor, etc.

### Template: Minimal Correct Command

```ts
import { commands, window, ExtensionContext } from 'vscode';
import { MyService } from '../services/MyService';

/**
 * Registers the 'myext.doAction' command.
 * @param context - The extension context for subscription management.
 * @param service - The injected service handling business logic.
 */
export function registerDoActionCommand(
  context: ExtensionContext,
  service: MyService,
): void {
  context.subscriptions.push(
    commands.registerCommand('myext.doAction', async () => {
      try {
        await service.doAction();
        void window.showInformationMessage('Action completed successfully.');
      } catch (error: unknown) {
        const msg = error instanceof Error ? error.message : String(error);
        void window.showErrorMessage(`Action failed: ${msg}`);
      }
    }),
  );
}
```
